## 設定と認証情報

`run` と `config validate` は、`--config` で明示しない限り
`~/.config/ghalet/config.yaml` を使います。`status`、`doctor`、`apply`、`gc` は
`--config` を省略するとアクセス可能なデーモンを探索し、応答する相手が 1 件の場合だけ
自動選択します。複数ある場合は `ghalet list` で管理 UID、ソケット、稼働中の
スナップショットを確認し、`--config PATH` で選択してください。設定を明示した場合は、
別の設定を使うデーモンには切り替わりません。見つからない場合、管理コマンドは
ユーザーごとのデフォルト設定を使い、`gc` は従来どおりロック取得後にオフラインで
保守を行えます。`list --config PATH` は一覧を絞り込み、ファイルの存在は要求しません。

探索では、ファイルシステムの権限に従って `/tmp/ghalet-<UID>/` の非公開 Unix ソケットに
問い合わせます。通常は管理ユーザー自身のデーモンのみが対象ですが、root は他ユーザーの
デーモンも探索できます。候補は 1 秒以内に応答し、返した設定パスがソケット名と
一致する必要があります。残存・無応答・無関係なソケット、シンボリックリンク、
非公開でないソケットは無視し、削除しません。PID やプロセス名による推測は行いません。
応答サイズの上限は 4 MiB です。操作時にも接続相手の UID を確認し、デーモンの設定が
選択したパスと一致しなければ操作を拒否します。
CLI の更新時はデーモンも再起動してください。旧デーモンは新しい設定照合付きの要求を拒否します。

設定ファイルはカレントディレクトリや `/etc` から探索しません。相対パスの基準は、
シェルのカレントディレクトリではなく、選択した設定ファイルのディレクトリです。
サービス定義には絶対パスを使ってください。YAML 内の `~` は展開されません。

systemd の `STATE_DIRECTORY` と `CACHE_DIRECTORY` が設定されている場合は優先し、
実行ディレクトリと復旧状態は `$STATE_DIRECTORY/runs`、runner のアーカイブと
ダイジェストは `$CACHE_DIRECTORY/runners` に保存します。
各変数には単一の絶対パスを指定し、相対パスやコロン区切りの複数パスは拒否します。
これらは XDG の基準ではなくアプリ専用のディレクトリです。
[systemd のディレクトリ管理](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#RuntimeDirectory=)を参照してください。

未指定の場合、実行ディレクトリと復旧状態は `$XDG_STATE_HOME/ghalet/runs`
（デフォルト: `~/.local/state/ghalet/runs`）、runner のアーカイブと公式 SHA-256
ダイジェストは共通の `$XDG_CACHE_HOME/ghalet/runners`
（デフォルト: `~/.cache/ghalet/runners`）に保存します。
XDG 変数が未設定・空・相対パスの場合は、これらの HOME 基準のデフォルトを使います。
保存先は `runner.user` や設定ファイルの場所ではなく、管理プロセスの環境に従います。
同じ実行領域を使えるデーモンは 1 つだけです。複数起動する場合は state の保存先を分けてください。
これらの保存先は YAML では設定できません。

ファイルを編集するだけでは、稼働中の設定も制御ソケットのアドレスも変わりません。
アドレスは正規化した設定ファイルの絶対パスから決まります。
デーモンに接続する管理コマンドは、設定が不正でもファイルが削除されても、
稼働中のスナップショットを参照します。反映可能な設定と再起動が必要な変更は
[設定反映](#設定反映)を参照してください。

`examples/config.yaml` にはリポジトリ、Organization、`gh`、PAT、App の例があります。
各 target は登録先の `scope` を持ちます。`credential` を省略すると
`defaults.credential` を継承し、共通設定もなければ `type: gh` を使います。
target に明示した `credential` は共通設定を丸ごと置き換えます。
空のマッピングは継承せず `gh` を選びます。認証設定内で `type` を省略した場合も `gh` です。
PAT / App を使う場合は、`type: pat` または `type: github-app` の明示が必要です。
認証方式固有のフィールドだけで方式が自動選択されることはありません。
明示的に空の type を指定すると拒否されます。
GitHub.com では、`scope` にリポジトリの `OWNER/REPO`、または Organization の
`ORG` を指定できます。これらは検証・認証・登録の照合前に HTTPS URL に正規化されます。
完全な HTTPS URL も指定でき、GitHub.com 以外のホストでは必須です。
対応する scope はリポジトリと Organization のみです。`runnerGroup` は
Organization 専用です。target ごとに scope は 1 つだけ指定できます。
必須の `id` は、管理コマンドとローカルステートで target を識別します。
省略可能な `scaleSet` のデフォルトは `id` です。GitHub 上の登録名と workflow の
`runs-on` ラベルを変えたい場合や、異なる scope で同じ名前を使う場合は明示してください。
ID は全 target 間で一意とし、先頭を英数字とする 1〜64 文字の ASCII 英数字・
アンダースコア・ハイフンで指定します。
App の `installationId` は credential ではなく target に属するため、
複数のインストールで 1 つの App キーを共有できます。

[コメント付きサンプル](../examples/config.yaml)の任意の `yaml-language-server` コメントで、
`schema.yaml` をエディターの補完・検証用に指定できます。設定バージョンのフィールドは
不要です。登録先の重複、最小容量、
管理ディレクトリの安全性などの制約も確認するには `ghalet config validate` を使ってください。

古い設定では `apiVersion` を削除し、トップレベルの `scopes` / `credentials` を
各 target に移してください。`scopeRef` / `credentialRef` は使いません。
`scaleSetName` は `scaleSet` に変更します。これらの旧キーとその他の未知のキーは、
GitHub への操作を行う前に拒否されます。

デフォルトの `gh` 認証では、ghalet の実行環境に GitHub CLI をインストールし、
実際にサービスを起動するアカウントでログインしてください。ghalet は 15 秒の期限で
`gh auth token --hostname HOST` を実行し、トークンを設定ファイルには書き込みません。
対話ユーザーのキーチェーンにログイン情報があっても、別のサービスユーザーや
ロック中のキーチェーンから使えるとは限りません。実際のサービス環境・ユーザーで
コマンドを確認してください。GitHub CLI や認証情報がなければエラーになり、
別の認証方式にはフォールバックしません。

PAT では `tokenEnv` と `tokenFile` のどちらか一方だけを指定します。
App の秘密鍵を含む認証ファイルは、所有者のみアクセスできる通常ファイルにしてください
（通常は `chmod 600`）。YAML に値を直接書くことはできません。
systemd の credential は、対応する `LoadCredential=` または
`LoadCredentialEncrypted=` とともに、
`/run/credentials/ghalet.service/` 以下の絶対パスを `tokenFile` または
`privateKeyFile` に指定して参照できます。不要に `Environment=` や workflow
ファイルへシークレットを置かないでください。暗号化登録、共通設定、ローテーションは
[暗号化した認証情報](credentials.ja.md)を参照してください。

scope 別の権限、PAT の作成、GitHub App のインストールは
[認証のセットアップと最小権限](authentication.ja.md)を参照してください。
group のアクセス設定と App のインストール範囲は別です。
group の作成とリポジトリへのアクセス許可は、先に GitHub 側で行ってください。
ghalet は runner group の作成・アクセス設定変更・削除を行いません。

SDK は PAT / App による管理トークンの更新に対応しますが、認証情報を継続的に
再取得できる登録トークン専用プロバイダーは提供しません。
登録トークンのみのモードは提供しません。

## 直接実行と環境

```sh
ghalet config validate --config /path/to/config.yaml
ghalet run --config /path/to/config.yaml
```

`runner.user` で別の既存アカウントを指定しない限り、ジョブは起動ユーザーで実行します。
ユーザーの切り替えには root が必要です。root で起動する場合は、非 root の実行ユーザーを
明示する必要があります。ghalet はユーザーを作成・削除せず、root ジョブは拒否します。
公式 runner は、自身のディレクトリからファイルシステムの root まで、すべての親で
一覧取得と通過ができる必要があります。管理対象の実行用親ディレクトリ（`workRoot`、
target、run）は `0755` で作成し、既存の `0711` は使用時に移行します。
Linux パッケージは `/var/lib/ghalet` も `0755` に移行します。
ディレクトリ名は見えますが、所有者は管理ユーザーのままで、他ユーザーは書き込めません。
ステートファイルとロックファイルは所有者のみアクセスできます。
管理対象外の親ディレクトリは変更しないため、runner ユーザーが一覧取得・通過できるようにしてください。
管理ディレクトリのパスにシンボリックリンクを含めることはできません。
macOS では `/var` のリンクではなく、`/private/var/...` のような正規パスを使ってください。

runner の起動とアクセス確認では、コントローラーの環境変数を継承しません。
HOME、USER、LOGNAME は実行ユーザーのアカウントから設定します。
コントローラーと runner のユーザーが異なる場合も同じです。
PATH のデフォルトは `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` で、
macOS では先頭に `/opt/homebrew/bin:/opt/homebrew/sbin` が加わります。
ログインシェルやシェルの初期化ファイルは読み込みません。

ユーザーがインストールしたツール、ロケール、プロキシなどには、
`runner.env` で環境変数の追加や PATH の上書きを明示してください。
コントローラーのトークン変数、SSH エージェントのソケット、ツールの設定パスなどは
自動ではコピーされません。管理用認証情報、アカウント識別情報、runner の入力変数は
`runner.env` では設定できません。runner の入力名は大文字・小文字を区別せず検査します。
JIT シークレットは `ACTIONS_RUNNER_INPUT_JITCONFIG` としてのみ渡し、
コマンドライン引数やステートのフィールドには入れません。管理用シークレットを
意図的に別の変数へコピーしないでください。runner 自身のファイルは実行専用
ディレクトリ内に置き、実行後に削除します。

これは runner の環境を最小化するものであり、認証・API 呼び出し・ダウンロードに使う
コントローラーの環境は変わりません。ファイルシステムやキーチェーンへのアクセスには、
[信頼境界](#信頼境界)で述べる制約が残ります。

ビルドツールと公式 runner が要求する OS の依存パッケージは、事前にホストへ
インストールしてください。Docker actions、ジョブコンテナ、サービスには対応していません。
Linux / macOS でのネイティブ実行には、Docker デーモン、Kubernetes、VM ランタイム、
サービスマネージャーは不要です。固定したバージョンから、macOS ARM64/x64 と
Linux ARM64/x64/ARM の runner パッケージを選択します。Windows には対応していません。

`runner` は全体共通の省略可能な設定です。バージョンのデフォルトは ghalet に
組み込まれた数値バージョンで、別のリリースを固定するには `runner.version` を指定します。
Renovate が公式の安定版を毎週確認し、組み込みのデフォルトとサンプルを
まとめて更新する PR を作成します。変更は通常の CI で検証します。
設定でバージョンを固定していなければ、ghalet の更新と再起動で
新しいデフォルトが適用されます。起動時に `latest` を解決することはなく、
runner の自己更新は無効のままです。

固定バージョンのアーカイブは `actions/runner` のリリースから取得し、
リリースアセットの公式 SHA-256 ダイジェストで検証します。
キャッシュ済みアーカイブの再利用時にも再検証します。公式ダイジェストのない
リリースはエラーにして使用しません。runner キャッシュに固定ダイジェストと
アーカイブを保存し、実行ごとの独立した実行ディレクトリに展開します。
破損キャッシュを黙って置き換えることはありません。示された不正なアーカイブを削除して
再起動してください。

## 容量・再試行・停止

`scaling` は省略可能です。各 target のデフォルトは `minRunners: 0`、
`maxRunners: 2` です。省略フィールドはデフォルト値を維持します。
`maxRunners: 0` の明示は不正です。

目標数は `min(maxRunners, assignedJobs + minRunners)` です。
実行中ジョブ、起動中の実行、確認できない復旧対象は、同じ共有容量を使用します。
受付済みジョブは、別 target の待機中の warm runner より優先されます。
前のプロセスグループの停止が確認できるまで、枠は再利用しません。
需要が減っただけで実行中の runner を停止することはありません。

各 listener が通知する容量の上限は `min(target.maxRunners, capacity.maxRunners)` です。
その時点の空きプロセス数ではないため、warm pool が埋まっても他の target が
GitHub から見えなくなることはありません。ジョブの取得は別途、共有の未完了ジョブ枠に
対して直列化します。取得応答が保留中の場合は、次の確定的な統計メッセージまで枠を予約します。
スケーリングの需要には `TotalAssignedJobs` を使い、ジョブメッセージの数は使いません。
公式 Listener のコールバック成功後に確認応答を返します。再配信でも処理の冪等性を
保つ必要があります。target 間の公平性や、複数ホストからの分散書き込みには対応していません。

準備の期限は 10 分、API 操作は 45 秒、認証コマンドは 15 秒、listener のポーリングは
60 秒です。登録・listener の失敗と準備・起動の失敗は、1/2/4 秒の指数バックオフで
最大 4 回試行します。SDK で判別可能な恒久的な不正リクエスト・認証エラーは
直ちに停止します。準備開始は target ごとに毎秒 1 回までです。
再試行を使い切った target は `apply` または通常停止・再起動まで障害状態に残り、他の target は
継続します。workflow の実行結果に対する再試行は ghalet では行いません。

SIGINT / SIGTERM は通常停止時に全 target の drain を開始します。
`apply` も設定切り替え前に全 target を drain します。
通常停止では Scale Set を残します。
新規取得と待機 runner の補充は止まりますが、割り当て済みで未起動のジョブには、
target・ホスト両方の上限内で引き続き runner を用意できます。
drain の期限は各 runner の起動時ではなく、要求時から計測します。
`drainTimeout` のデフォルトは 10 分です。期限後は準備をキャンセルし、
確認済みのプロセスグループに、実行中ジョブを含めて SIGTERM を送り、
残っていれば SIGKILL を送ります。コントローラーは runner のプロセスグループの停止と、
ローカルの終了・出力監視の完了を待って終了します。
識別できない実行に名前や PID だけを根拠にシグナルを送ることはなく、
そのグループが存在しないと確認するまで停止完了を待ち続けます。
記録と診断情報は調査用に残ります。存在しないことの確認だけでは cleanup は許可しません。
強制停止は成功ではなく未完了として報告します。

再起動が必要な変更では、デーモンを通常停止し、正常完了を確認してから
再起動してください。フォアグラウンドでは `ghalet run` の終了コードを、
サービス管理下では停止コマンドの結果だけでなく、デーモンの終了結果とログを確認します。
強制終了や不完全な drain の後には再起動せず、診断情報を調べ、
保留中の実行や cleanup の失敗を解消してください。

Linux / macOS ともに、直接起動かサービス管理下かにかかわらず、新しい runner ごとに
小さなフォアグラウンドの guard をプロセスグループのリーダーとして置きます。
永続化を伴う起動ゲートはコントローラーの生存確認も担います。
コントローラーが終了・強制終了するとパイプが閉じ、
guard が自身を含むグループ全体に SIGKILL を送ります。
生存中のリーダーがグループ ID を保持するため、不確かな PID の推測には依存しません。
runner の通常終了は別途報告し、その後に TERM、2 秒の猶予、
最後にグループ全体への KILL を行います。終了診断には guard の意図的な SIGKILL ではなく、
runner の実際の実行結果を使います。guard はステートを書き換えず、ログも削除しません。
そのファイルディスクリプターは runner に継承されません。
これは子プロセスの監視であり、自己デーモン化や隔離ではありません。
信頼したジョブが guard を停止したり、グループから逃れたりしないことが前提で、
カーネル・ホスト障害では監視が中断され得ます。

## 設定反映

```sh
ghalet apply --config /path/to/config.yaml
# パッケージの systemd サービス:
sudo systemctl reload ghalet
```

target、上限、認証情報、runner バージョン、環境変数、タイムアウト、ログ保存方針は、
設定を編集して `apply` で反映します。稼働中のデーモンが必要で、
そのデーモン自身の設定パスを再読込し、ファイルは変更しません。
設定が存在しないか不正な場合は失敗し、別のファイルで代用しません。

`apply` は反映処理の完了まで待ちます。
新設定を検証してから新規受付を止め、旧設定の上限・タイムアウトで全 target を drain し、
listener を閉じた後、新設定の target を登録して listener の初期化を待ちます。
変更のない Scale Set は再利用します。起動失敗は apply の結果に含め、
その後の listener の障害は `doctor` で確認できます。
ローカルの `targets[].id` で追加・変更・削除を識別し、scope・group・Scale Set の変更時は
その target の登録を置き換えます。全 target を外すには `targets: []` を指定します。
`targets` の省略や null は不正です。

削除・置換された target の Scale Set は、新設定の target が同じ scope と登録 ID
（または scope・group・名前）を参照しておらず、ローカルの実行も残っていない場合に
削除を試みます。drain と listener の後始末が正常完了し、GitHub の統計でも
受付済みジョブや登録済み runner がないことを確認します。runner group は削除しません。
管理する Scale Set を他のコントローラーと共有しないでください。

失敗は target ごとに報告し、非ゼロで終了しますが、正常な target には新設定を反映します。
自動ロールバックはしません。削除に失敗した登録の旧クライアントはメモリー内に保持し、
`apply` で再試行できます。強制 drain、不確実な実行、listener の終了失敗は調査が必要です。
保留中の削除処理は再起動をまたいで永続化しません。クラッシュ後は現在の設定を正とし、
到達できない旧登録は GitHub 上で手動削除が必要になることがあります。
空き容量を作るために保留中の実行記録を破棄しません。同時の apply は拒否し、
停止要求では apply を中断します。CLI が切断・タイムアウトしてもデーモン側では処理を
継続するため、再試行前に `status` と `doctor` を確認してください。

実行ユーザーと管理ディレクトリの変更には通常停止・再起動が必要で、
drain 前に拒否します。環境変数や systemd が復号した認証情報ファイルは稼働中サービスに
属し、付属の unit でその入力を更新するにはサービスの再起動が必要です。
通常の認証情報ファイルは apply で新クライアントを作る際に再読込します。
付属の systemd unit は `ExecReload` から同期的に `ghalet apply` を実行し、
`TimeoutStartSec` で 15 分の期限を設けます。drain の期限や target 数を増やす場合は、
reload の期限と `TimeoutStopSec` を延ばしてください。
`systemctl daemon-reload` が読み直すのは unit 定義であり、ghalet の設定ではありません。

## 診断・ガベージコレクション

```sh
ghalet status --config /path/to/config.yaml
ghalet doctor --config /path/to/config.yaml
ghalet gc --config /path/to/config.yaml --dry-run
ghalet gc --config /path/to/config.yaml
```

管理コマンドの応答は JSON です。`status` は、不健全な状態であってもスナップショットを
取得できればゼロで終了します。`doctor` は診断上の問題が 1 つでもあれば非ゼロになります。
`gc`、`apply` は、失敗・未完了の部分があれば非ゼロになり、
個別の結果を含めます。管理操作の一部が失敗しても、デーモンは終了せず、
成功済みの cleanup も巻き戻しません。

接続中の GC はデーモンが実行し、実行時ステートと直列化します。
接続できない場合、直接実行する GC でも、同じ workRoot の OS ロックと
設定の制御アドレスのロックを取得する必要があります。
ソケットへの接続失敗だけでは、既存デーモンを迂回する根拠にはなりません。
ロックファイルは PID ファイルではなく、プロセス終了後も残ることがあります。
オフライン GC でサービスの状態を参照するには、サービスと同じ保存先の環境変数を指定してください。
配布用サービスでは `STATE_DIRECTORY=/var/lib/ghalet` と
`CACHE_DIRECTORY=/var/cache/ghalet` です。

クラッシュ後は、記録を現在明示している登録、プロセスの UID・グループ・カーネルの
開始識別情報、および生存中の実行では GitHub runner ID と照合します。
Linux の識別にはブート ID と `/proc` の開始 tick、macOS ではマイクロ秒精度の
カーネルのプロセス開始時刻を使います。プロセスの生存確認は、登録や実行ユーザーとの
照合とは独立して行います。プロセスの停止を検証できた記録は、ターゲットの削除、
認証失敗、登録やユーザーの不一致により cleanup ができない場合でも容量を予約しません。
記録・ファイル・診断は保持し、停止しただけでは削除を許可しません。
生存している可能性がある、または検証できないプロセスは保守的に容量を予約します。
破損記録も、プロセス不在を証明するための信頼できる識別情報がないため容量を予約し、
cleanup を許可する根拠には使いません。
生存プロセスを復旧しても `Wait` の関係を再構築したり、終了コードを作り上げたりはしません。
元のプロセスグループ内で観測した子孫は復旧できますが、
グループから逃れた子孫を完全に検出・隔離することはできません。

空またはゾンビのみのプロセスグループのスナップショットには、カーネルでの再検証が必要です。
Linux では列挙した各 PID のカーネル上のグループ所属を `/proc` の状態取得より先に確認し、
対象グループ外と確認できた PID の状態を読み取れることは要求しません。
既知のグループメンバーが消失した場合は、回数を制限して再試行します。
所属不明の PID が消失した場合は、消失前に fork した子を発見できるよう再列挙し、
対象グループが既知の単一スレッドのゾンビだけであることを再確認します。
この回数制限付きの確認は無関係な PID の増減を許容しますが、信頼済みジョブを前提とし、
意図的にタイミングを合わせて fork と終了を連鎖させる動作に対するアトミックな
スナップショットは提供しません。
macOS では `kern.proc.pgrp` を照会します。グループが存在しない場合、
または新たに取得した全メンバーが、同じカーネル識別情報を持つゾンビとして既に観測済みの
場合にのみ、停止済みと扱います。新たに観測したゾンビは直前に fork した可能性があるため、
安全の根拠にはできません。検証に失敗した場合は不確実な状態と容量の予約を維持します。
ステートファイルは末尾の改行込みで 1 MiB が上限です。
シグナル送信前に大量の子孫リストを永続化できない場合も含め、上限を超える保存は失敗し、
最後に読み取り可能だった記録を置き換えません。

手動復旧では、示されたパスとプロセスを調査し、識別した実行だけを待つか明示的に停止して、
`gc --dry-run` と `gc` を実行してください。設定や権限の問題を直して再起動し、
再検証します。空き容量を作るためにステートだけを削除しないでください。
破損記録の修復・削除前には、実際の実行を手動で調査する必要があります。

## ログ

デーモンの標準出力は JSONL のみです。フィールドは `time`、`level`、`msg`、
任意の `event`、`scope`、`targetId`、`runId`、数値の `durationMs`、`error` です。
レコード内の改行はエスケープし、runner の出力は標準出力に混在させません。
構造化フィールドの選別、転送、OTel への変換は外部の収集ツールで行ってください。
組み込みの HTTP ヘルスエンドポイント、メトリクス exporter、OTel SDK、
collector への依存はありません。

runner 開始イベントとアーカイブのメタデータの `scope` は登録先 URL です。
旧ステートの `scopeRef` は読み取り可能ですが、認証情報の選択や登録の識別には使いません。

`logs` は runner ログの保存設定で、デーモンの標準出力・標準エラーは対象外です。
`logs.preserve: true` では、実行領域の削除前に `output.log` と `_diag/**/*.log` を
`logs.root/runs/RUN_ID` に退避します。`logs.root` のデフォルトは
`STATE_DIRECTORY` が設定されていれば `$STATE_DIRECTORY/logs`、
それ以外は `$XDG_STATE_HOME/ghalet/logs` です。
`XDG_STATE_HOME` も未設定・空・相対パスの場合は `~/.local/state/ghalet/logs` になります。
明示した `logs.root` はこのデフォルトを
上書きします。相対値は引き続き選択した設定ファイルのディレクトリを基準に解決します。
認証情報と workspace の内容は退避しません。
退避失敗時は元のログとステートを保持します。プロセス停止確認後のファイル削除だけの失敗は
実行容量を占有せず、`gc` または次回起動で再試行します。
`logs.retention` は正常に保存済みのアーカイブだけを期限切れ削除し、毎時の確認も行います。
ディスク容量制限、空き容量監視、外部への自動ログ転送はありません。

実行中の出力取得と診断ログの退避では、各行を改行抜きで 64 KiB に制限します。
上限を超える行は全体を省略し、`[ghalet: log line over 64 KiB omitted]` に置き換えて、
次の改行から取得を再開します。メモリー使用量を制限しつつ、行の部分出力による
シークレットの漏洩を防ぎます。通常の行では、書き込み境界をまたぐマスキングと
起動完了の検出に対応します。

既知の管理用認証値と JIT 値はマスキングします。App の秘密鍵を含む複数行の値は、
空白以外を含む各行も個別にマスクし、共通部分は最後の登録が解除されるまで保持します。
元のテキスト上で一致箇所を検出し、重複する一致は登録順に関係なくまとめてマスクします。
ジョブのシークレットを runner 自身のログでマスクする責任は、公式 runner が持ちます。
信頼した workflow が意図的に変形・出力する任意のシークレットを、
すべてマスクできる仕組みはありません。

## サービスとしての常駐化

Linux パッケージや Docker Compose で導入する場合は、
[パッケージとコンテナ](distribution.ja.md)を参照してください。
以下はサービスを手動で導入する場合の手順です。

Linux では、専用の `ghalet` ユーザーを事前に作成し、
`examples/ghalet.service` を `/etc/systemd/system/` にコピーして、
`/etc/ghalet/config.yaml` に設定を配置します。unit は `StateDirectory=ghalet` と
`CacheDirectory=ghalet` で `/var/lib/ghalet` と `/var/cache/ghalet` をサービスユーザー用に
作成し、`STATE_DIRECTORY` と `CACHE_DIRECTORY` で渡します。XDG の上書きは不要です。
`logs.root` は、state 配下のデフォルト保存先を変更する場合のみ指定してください。
そのユーザーで認証と設定検証を行い、`systemctl enable --now ghalet` を実行します。
`KillMode=mixed` は最初の停止シグナルをコントローラーだけに送り、
ジョブの drain と runner グループの停止を行ってから終了できるようにします。
有限の `TimeoutStopSec=15min` は独立した最終期限です。
コントローラーがハングしたり、残存グループを検証できなかったりした場合、
systemd はコントローラーと runner を含むサービスの cgroup 内の全残存プロセスを
強制停止します。コントローラーのクラッシュ・終了時にも残存プロセスを停止します。
この最終手段は、復旧のために runner を生存させることより後始末を優先するものです。
中断後の復旧用にステートとログは残ります。サービスの期限は設定した drain 期限より長くし、
プロセス停止、API 呼び出し、cleanup の時間も確保してください。
サンプルでは 5 分を追加しています。ホスト停止や電源断によるジョブ中断は防げません。

macOS ネイティブでは `examples/com.github.ghalet.plist` の絶対パスを調整し、
ログディレクトリを作成して、`~/Library/LaunchAgents/` に配置します。
`launchctl bootstrap gui/$(id -u) FILE` で登録してください。
サービスの停止上限 900 秒は、デフォルトの drain 10 分に 5 分を加えたものです。
設定で期限を変えた場合は、この値も増やしてください。
ゼロは launchd が停止を無期限に待つ意味になるため、意図的に避けています。
`AbandonProcessGroup` は false で、launchd がコントローラー自身のグループも cleanup
します。別の runner グループには[前述の guard](#容量再試行停止)を使います。
LaunchAgent はログイン時に起動し、ログイン前には起動しません。スリープも防ぎません。
別の実行ユーザーを使う場合は、管理者が管理する LaunchDaemon と `runner.user` を
使ってください。LaunchAgent がユーザーを切り替えられるとは想定しないでください。
実際のログイン・サービス環境で、キーチェーンへのアクセスと停止動作を確認してください。

Apple Silicon の Lima では、`examples/lima.yaml` が VZ、4 vCPU、8 GiB メモリー、
80 GiB ディスク、ホストマウントなし、containerd なしの Ubuntu 26.04 ARM64 VM と、
インストール・有効化済みの systemd サービスを用意します。
プロビジョニングはホストの認証情報をコピーしません。
Go の toolchain 選択機能を使い、公開済みの ghalet モジュールをビルドします。
未公開の変更を試す場合は、ローカルでビルドした Linux ARM64 バイナリをコピーしてください。
`limactl copy` で設定を明示的にコピーし、ゲストの `ghalet` ユーザーでログインするか、
ゲスト専用の認証情報を渡してサービスを起動します。
設定ファイルが存在するまで、サービス起動は条件付きでスキップされます。

`examples/com.github.ghalet-lima.plist` は作成済み VM をログイン時に起動します。
limactl のパスとインスタンス名を調整してください。
ジョブごとの VM 再起動や、Mac のスリープ・ログアウト中の動作は保証しません。
`limactl list` とゲスト内のマウント出力で、macOS ホストの共有が公開されていないことを
確認してください。VM のライフサイクル、スリープ・復帰、電源断は運用者による
受け入れ確認の対象であり、テンプレート検証だけでは確認できません。

## 信頼境界

**Ephemeral な登録は隔離ではありません。** 信頼できるリポジトリの信頼できる
workflow にだけ使用し、悪意ある fork PR は実行しないでください。
各 runner は別の実行・作業パスを持ちますが、OS、実行ユーザーの HOME、
キャッシュ、ツール、ネットワーク、既存の権限を共有します。
ジョブはその共有環境を変更できます。GitHub CLI やキーチェーンを含む、
実行ユーザーの保存済み認証情報にアクセスできる場合もあります。
トークン変数の除去やジョブ専用の `GH_TOKEN` の指定では、その保存領域を隔離できません。
認証情報を分けるには別の実行ユーザーを使ってください。
デフォルトの同一ユーザーモデルでは、コントローラーのファイルやプロセスもジョブから
アクセス可能です。ファイル権限、マスキング、非公開ソケットは、
そのユーザーに対するセキュリティ境界にはなりません。
追加の sudo 権限や Docker ソケットは提供せず、root ジョブも拒否しますが、
既存の権限は剥奪しません。専用アカウント / VM と適切なホスト側の制御を使ってください。
